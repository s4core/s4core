# S4 Architecture Documentation

## Overview

S4 is built as a single-node, high-performance object storage server with a focus on simplicity, reliability, and solving the inode exhaustion problem.

## System Layers

```
┌─────────────────────────────────────────┐
│  LAYER 1: Network & Protocol (Axum)    │
│  HTTP/1.1, HTTP/2, HTTP/3 QUIC         │
│  AWS Signature V4 Auth                 │
└──────────────────────────┬──────────────┘
                           ⬇
┌─────────────────────────────────────────┐
│  LAYER 2: Business Logic               │
│  • Deduplication Engine (CAS)           │
│  • Atomic Directory Operations          │
│  • ACL / Policy Check                   │
└──────────────────────────┬──────────────┘
                           ⬇
┌─────────────────────────────────────────┐
│  LAYER 3: Storage Engine (Bitcask)      │
│  • Hot Index: fjall (LSM, MVCC, LZ4)  │
│  • Cold Data: Append-only Log Volumes  │
│  • Compactor (Background GC)            │
└─────────────────────────────────────────┘
```

## Storage Engine

### Design Principles

1. **Append-Only Logs**: All writes are sequential (maximum disk performance)
2. **Metadata Separation**: Fast metadata in ACID database (fjall)
3. **Content Deduplication**: Same content stored only once
4. **Crash Recovery**: Metadata can be rebuilt from volume headers

### Storage Strategy

- **All Objects**: Stored in append-only volume files (volumes are the single source of truth for object data)
- **Metadata**: Stored in fjall database with separate keyspaces (objects, versions, buckets, IAM, dedup)

### Volume Structure

Volume files are named `volume_XXXXXX.dat` where XXXXXX is a zero-padded volume ID.

Each blob in a volume has the structure:
```
[BlobHeader (serialized)] + [Key (UTF-8 bytes)] + [Data (raw bytes)]
```

The `BlobHeader` contains:
- CRC32 checksum
- Timestamp
- Key length
- Blob length
- Flags (deleted marker, multipart, etc.)

A volume is one blob after another, and the offset `VolumeWriter` reports for a blob is where its
header starts. That holds even when a write is dropped halfway — an RPC whose client hung up, an
HTTP request whose client timed out: whatever the dropped write already handed to the file is cut
off before the next write, which starts exactly where the last whole blob ends. No index record can
point into those bytes, because `IndexRecord` is committed only after its blob is whole.

### Index Database

The fjall database stores `IndexRecord` entries across multiple keyspaces:
- **objects**: bucket/key → Volume ID, Offset, Size, Metadata, Content Hash
- **versions**: bucket/key → Version list
- **buckets**: bucket_name → Bucket configuration
- **iam**: user/key → IAM records
- **dedup**: content_hash → DedupEntry (ref count, volume location)
- **version_digests** (cluster mode only): ring position ‖ bucket/key → HLC, origin node, ETag hash and kind of the version a replicated key holds; see Anti-Entropy below
- **cluster_meta** (cluster mode only): the layout version of the digests and the node's tombstone horizon, the configurations adopted, the stage of the bucket metadata placement and the durable pool generation

This allows:
- Fast lookups (O(log n) with LSM-tree)
- Lock-free concurrent reads (MVCC)
- Atomic cross-keyspace batch writes
- Native prefix scans (O(log n) seek, not full table scan)
- Built-in LZ4 compression

## Data Flow

### Write Path (PUT Object)

1. Client sends PUT request with data
2. Compute SHA-256 hash of data
3. Check deduplicator: does this content already exist?
   - If yes: Create new index entry pointing to existing blob (reference counting)
   - If no: Write blob to current volume, register in deduplicator
4. Create IndexRecord with metadata
5. Store IndexRecord in fjall (atomic batch write)
6. fsync volume file (if strict_sync enabled)
7. Return 200 OK to client

### Read Path (GET Object)

1. Client sends GET request
2. Lookup IndexRecord in fjall by key (lock-free MVCC read)
3. If not found, return 404
4. Read blob from volume file at (volume_id, offset)
5. Verify CRC32 checksum
6. Return data to client

### Delete Path (DELETE Object)

1. Client sends DELETE request
2. Lookup IndexRecord in fjall
3. Mark blob as deleted (tombstone in volume or index)
4. Remove IndexRecord from fjall (atomic batch)
5. Update deduplicator (decrement reference count)
6. Return 204 No Content

## Deduplication

Content-Addressable Storage (CAS) is implemented using SHA-256 hashes:

- Before writing, compute hash of content
- Check if hash exists in deduplicator map
- If exists: Create new index entry pointing to existing blob
- If not: Write new blob and register hash

This saves 30-50% storage space for typical workloads with duplicate content.

Reference counts — the `DedupEntry` of a blob, the committed and staged counts of a multipart part or
manifest in `blob_refs` — change only through read-modify-write actions of a batch
(`IncrementDedupRef`, `DecrementDedupRef`, `UpdateDedupLocation`, `AdjustBlobRef`, `RelocateBlobRef`
in `s4-core/src/storage/index.rs`). `batch_write` runs them under one lock, reading each count as the
actions before it in the same batch left it, so concurrent batches and several changes of one count
in one batch all count. The lock is released after the batch commits and before its fsync: fjall
keeps one journal per database and appends batches in seqno order, so a later batch's fsync makes
every earlier one durable, and each batch still answers only after its own fsync. Every write that
replaces a record releases the old one's data in its batch, a multipart completion included.

## Atomic Operations

Directory operations are atomic because "directories" are virtual - they're just key prefixes in the index database.

To rename a directory:
1. Start atomic batch in fjall
2. Find all keys with old prefix
3. Update all keys to new prefix (in-memory operation)
4. Commit transaction

This takes milliseconds even for millions of files because we're only updating metadata, not moving data.

## Crash Recovery

If the process crashes:

1. On startup, scan all volume files
2. Read BlobHeader from each blob
3. Reconstruct index database from headers
4. Rebuild deduplicator map

This ensures data integrity even if the metadata database is lost. The fjall WAL provides instant crash recovery in the normal case.

An index counts as lost only when it holds no record at all — no object, version list, bucket marker
or IAM record (`IndexDb::has_no_records`) — while volume files exist. An index whose objects were all
deleted still holds its buckets and, with a root configured, its IAM state; taking it for a lost one
would rebuild it from volumes that still hold the deleted objects' bytes and bring them back. Recovery
replays the metadata journal when it has entries, otherwise the volume headers.

## Volume Compaction (s4-compactor)

S4 uses append-only volume files — when objects are deleted or overwritten, the old
blob data remains as dead space. The compactor reclaims this space:

### How It Works

1. **Discover** all volume files (skipping the currently active one)
2. **Build dedup index**: `(volume_id, offset) → content_hash` from the dedup keyspace, and the
   blob-ref index of the live entries of `blob_refs`
3. **Keep what live records reach**: every blob a live record of the objects, buckets or IAM keyspace
   reaches — a plain object's blob, a composite object's manifest and segments, an open upload's
   parts — is live whatever the counts say (`keep_reachable_blobs`); such a blob without a live count
   is logged as reference count drift. A live segment or part whose blob has no entry to locate it
   stops the run. A count that drifted low costs space at worst, never data
4. **Analyze** each volume — scan all blobs, classify as live or dead based on these indices
5. **Compact** volumes where fragmentation exceeds the threshold (default: 30% dead space):
   - Copy live blobs to a new volume via `VolumeWriter`
   - Atomically update all `IndexRecord` and `DedupEntry` locations in a single fjall batch — the
     records of the objects, buckets (markers) and IAM keyspaces, the same ones step 3 keeps alive —
     with a journal entry for each record moved (`VolumeCompactor::with_journal`, the engine's own
     journal): a recovery from the journal then finds the record where it is, not in a volume this
     run deleted
   - Rename old volume to `.dat.compacted`, then delete (crash-safe two-phase removal)
6. **Report** statistics: volumes compacted, bytes reclaimed, errors

Before step 2 the orphan purge removes dedup and blob-ref entries no live record reaches; when a live
manifest cannot be read it removes no blob-ref entry in that run.

### Two Compaction Modes

- **Regular** (every N hours, default 6): processes up to 10 volumes per cycle — lightweight, minimal I/O impact
- **Full** (once daily at configured time, default 02:00 local): processes all volumes with no limits — reclaims all dead space

The daily full compaction time is configurable via `S4_COMPACTION_FULL_TIME` (format: "HH:MM"). Set to empty string to disable.

### Key Invariants

- **Never lose confirmed data** — old volume is deleted only after all live blobs are verified relocated
- **Crash-safe** — incomplete compaction is recoverable (idempotent restart)
- **Non-blocking** — runs in background while normal reads/writes continue
- **Dedup-aware** — updates DedupEntry locations, not just IndexRecords

### Architecture

- **s4-compactor** crate provides `VolumeCompactor` (compaction) and `VolumeScrubber` (CRC32 integrity verification)
- **s4-server** runs a `CompactionWorker` background task (same pattern as `LifecycleWorker`)
- Compaction interval, threshold, and dry-run mode are configurable via environment variables

### Volume Scrubber

The scrubber verifies CRC32 checksums of all blobs in all volumes, detecting bit rot
or data corruption. It reports the number of healthy and corrupted blobs.

## Performance Characteristics

- **Write Latency**: ~1-2ms for small objects (limited by fsync)
- **Read Latency**: ~0.5-1ms (metadata lookup + disk read)
- **Throughput**: Limited by disk sequential write speed (~500MB/s on SSD)
- **Concurrency**: High (async I/O with tokio)

## Scalability & Federation

S4 supports two deployment modes:

### Single-Node Mode (Default)

Optimized for maximum performance on one machine. No distributed overhead. All data is stored locally.

### Distributed Mode (Federation)

S4 uses **leaderless quorum replication** for high availability. Any node can accept any request — there is no single leader.

```
                    ┌─────────────────────┐
                    │   Load Balancer     │
                    │   (HAProxy/Nginx)   │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
        ┌─────▼─────┐   ┌─────▼─────┐   ┌─────▼─────┐
        │  Node 1   │   │  Node 2   │   │  Node 3   │
        │           │◄─►│           │◄─►│           │
        │ S3 API +  │   │ S3 API +  │   │ S3 API +  │
        │ Storage   │   │ Storage   │   │ Storage   │
        ├───────────┤   ├───────────┤   ├───────────┤
        │ fjall     │   │ fjall     │   │ fjall     │
        │ volumes   │   │ volumes   │   │ volumes   │
        ├───────────┤   ├───────────┤   ├───────────┤
        │ Gossip    │◄─►│ Gossip    │◄─►│ Gossip    │
        │ (SWIM)    │   │ (SWIM)    │   │ (SWIM)    │
        └───────────┘   └───────────┘   └───────────┘
              Pool 1 (current generation)
```

**Key properties:**
- **Server Pools**: Each pool places data by a durable generation: an epoch and the ordered roster of its current owners. A pool grows by appending members to `S4_POOL_NODES` (Enterprise Edition; CE keeps a pool at three nodes): the next generation is prepared, every replicated key whose replicas change moves to its new owners in the background while writes reach both generations and reads follow each range's cut-over, and the pool settles on the grown generation (pool generations below). Members are never removed, replaced or reordered. A machine that comes up at a member's address with an identity of its own — a blank data directory without `S4_EXPECTED_NODE_IDENTITY` — is refused at start: the roster it names cannot reproduce the generation its peers announce. The error names the identity the generation holds that place for when gossip still knows it (`GenerationAnnouncement::holder_of`), and otherwise points to `GET /api/admin/cluster/topology`, where every node lists that member as not alive; a replacement takes the recorded identity. Retiring an identity that is lost for good in favour of another is planned in `plans/POOL-MEMBER-REPLACEMENT.md`.
- **Pool generations** (protocol 9, `s4-cluster/src/pool_generation.rs`, bootstrap in `s4-server/src/pool_generation.rs`): `PoolGenerationRecord` holds `current`, an optional append-only `proposed` successor at epoch + 1 and `moving`. It is fsynced in `cluster_meta` before announcement and published as `__system__/__s4_pool_generation_v1/<pool>` with an HLC through the current quorum, once every owner gossip holds alive answers `Health` with its identity (at most 30 s): gossip holds a node alive before its gRPC server listens, and a publication sent in that moment would fail calls and store hints for peers that were never down. The node logs whether it wrote the record or found it there. A restart cannot reorder, remove or replace recorded owners, propose another growth while one is pending, or roll back a begun move. Protocol 9 gossip appends a fourth tail after the existing adoption, bucket metadata and IAM tails: bounded stamps of both ordered rosters, including their epochs and fingerprints, plus the move and bootstrap flags. Growth readiness requires every proposed member alive at protocol 9 or newer, announcing the same durable generations, with bucket metadata settled, and every appended member reporting room for its share of the pool (what a node of the old ring stores now, scaled by the ratio of the rosters) with `S4_REBALANCE_MIN_FREE_RATIO` of its disk free on top. Once a persisted record is `moving`, the router divides the union of both rings into vnode arcs, writes every class through the old and successor quorum, and reads an arc through the old owners until its local `cut_over`, then through the successors. A local `cut_over` does not weaken writes: the joint rule remains until the future common finalization barrier, so coordinators applying the switch in any order stay safe. Replica RPCs carry the successor epoch as `placement_generation`; a replica in the move rejects an older coordinator before storage access, while read repair and other versioned repair copies may pass the fence. Read repair repairs only replicas that answered with an older version; owners the read did not ask are the move's, which keeps to its limits (a read repair per read and owner would copy the object on every read), and a fetch repair of a streamed GET or HEAD is scheduled only for objects up to 64 MiB, which a local target assembles in memory. A GET whose selected source took a newer version between the digests and the fetch — the key overwritten during the read — serves that version with its own ETag, HLC and metadata, as it would have selected it a moment later; a source holding another version that is not newer is refused, and the read selects its version again, up to three times. Before a part or the completion of an upload goes out through the joint quorum, the coordinator brings every replica of either generation that holds no session of it to it, while a write quorum of one generation holds it: from this node, or from a replica that holds it (`PoolMove` with `hand_over_upload`); an upload that could not be handed over answers `503` and no replica takes the operation, a completion is refused unless the replicas with a valid plan meet every requirement of the rule, and `NoSuchUpload` is answered only when no replica took the operation. Multipart hints are written only while the key's pool moves: a stable pool's hint log stays readable by the release before. An upload lives while a write quorum of either generation holds it open or completing; a session that a completion or an abort missed is stale — a multipart hint aborts it on its target, and the move never hands it over. While a pool is `moving`, every node of the old generation moves what it holds to the new owners (`s4-cluster/src/rebalance/`): each vnode arc, the replicated records of `__system__` without version digests (tiering policies, the roster and layouts of erasure sets, the pool generation) and the open multipart uploads are work items, walked a page at a time. No digest compares the records without digests and the uploads before their ranges cut over, so these two items are walked only once every member announced the move for longer than the arrival window of a write: from then on no write placed by the earlier generation reaches the old owners alone. A key is settled across both generations as anti-entropy settles it (newer wins; this node and the key's new owners must answer, the other old owners give their versions when they do); an erasure-coded object moves as its namespace entry; an upload moves as its session and the parts a replica lacks, each part read back against its CRC32 and SHA-256 and compared with the checksums the receiver computed. Copies a repair writes carry `verify_content`, and the receiver refuses one whose bytes differ from their SHA-256; the copy is then taken from another replica holding the same version. Every item's cursor, counts and the keys to retry are stored in `cluster_meta` after each page, and an operator's pause is stored too, so a restart of either side or of the whole pool continues where it stopped. The move keeps to `S4_REBALANCE_MAX_BYTES_PER_SEC`, `S4_REBALANCE_MAX_KEYS_PER_SEC` and `S4_REBALANCE_CONCURRENT_RANGES`, gives way while the node coordinates many client operations, and sends nothing to a receiver whose free share is below `S4_REBALANCE_MIN_FREE_RATIO`: the items sending to it wait with that reason. A key whose newest copy is one a failed write left (settling calls it ambiguous) still brings its new owners the newest version the old owners confirmed. **The transition** (`s4-cluster/src/rebalance/transition.rs`, `verify.rs`, driven from `s4-server/src/pool_generation.rs`): every node begins the move by itself once the readiness gate opens, or once any member announces it began; it stores `moving`, writes through both quorums, and raises its placement floor to the successor's epoch only once every member announced the move, so a member a moment behind is not fenced; a node restarted in the move raises it at once only when it had applied a range cut over, which happens only after every member began. The member with the lowest identity alive verifies the ranges once every member began for longer than the arrival window of a write and every member reports (`PoolMove` RPC) that it handed over what it held. Every owner of a range by either generation, in every class, reports its version digests of the range a page at a time (`RangeDigests` RPC), merged in ring order: for every key, the newest version that as many old owners as a write quorum hold or have passed must be covered by every new owner (a tombstone older than `gc_grace` may be absent); two versions of one HLC and kind with different ETags cannot be ordered by digests, so a key that falls short is first weighed by the total order of versions, and one every new owner already covers by it holds nothing back; a key that falls short is brought to its new owners and the range is checked again later, and no range is verified while a node keeps a hint for one of its new owners. Verified ranges are merged into the replicated record `__system__/__s4_pool_generation_v1/<pool>/cut-over/<epoch>` (joint quorum, HLC) and handed to every member; a member stores the ranges it applies in `cluster_meta` before reading them through the successor, and reads them back before serving after a restart. When every range cut over, every member reports every range applied and no placement decision reading through the old owners in flight (decisions hold a ticket), the leader writes the generation record `Stable(g + 1)` and hands it over; each member stores it with the moment, and from then on the successor alone places every key and writes need its quorum alone. A node that was away adopts the settling from its peers' announcements at start or from the replicated record. The topology epoch carried by replica calls stays the pool's first (`WIRE_TOPOLOGY_EPOCH`): generations are told apart by `placement_generation`, so settled and unsettled nodes keep talking and erasure sets keep their epoch. While the move runs, tombstone GC holds every tombstone; once settled, the successor's layout places tombstones and only rounds begun after the settling count, and anti-entropy compares by the successor's ring; two nodes announcing different current generations compare nothing. **Clean-up** (`s4-cluster/src/rebalance/foreign.rs`): once every member announces the settled generation and `gc_grace` passed since this node settled, the node walks its digests, its records of `__system__` without digests and its open uploads; a key it no longer owns is settled across its owners and this node (its copy weighed, never counted as confirming) and removed here only once the owners hold that version. A node that starts without a recorded generation first hands over, the same way, every copy it holds of a key the ring gives others — a pool grown by an earlier release — and removes them under the same conditions. For user objects this initial hand-over may spread the newest local version even when the owners cannot confirm its history, preserving writes acknowledged before generations existed. Bucket metadata never uses that override: an unconfirmed copy stays pending. A foreign bucket marker with a made-up HLC is excluded from reconciliation in both hand-over and clean-up, because an earlier replica could create it merely for an object it stored; its modification time must not override a real bucket deletion. After a verified growth, its aged foreign copy may be removed locally under the clean-up grace policy without spreading it to the owners. A younger marker remains pending. Completed clean-up progress from an earlier build with kept copies is scanned again only under this post-growth policy; legacy hand-over and completed passes with no kept copies stay complete. Each step names why it waits in the log. **Observability and pause** (`s4-cluster/src/rebalance/report.rs`): `PoolGrowth` reads the node's generation, its `PoolTransition` and the `RebalanceHandle` of its move, and answers `GET /api/admin/cluster/rebalance` (state `stable`, `prepared` or `moving`, both generations, the driver's reason to wait, the operator's pause, whether the earlier generation is fenced, ranges by state, and the move of this node's keys: items and ranges done, keys scanned and moved, bytes sent, waiting items with their reason, errors by reason, `remaining_bytes` — the node's stored bytes times the share, by ring length, of the arcs it owned by `g` that it has not handed over — and `eta_secs` from the pace since the move last ran unhindered); the same report sets `s4_pool_generation{pool}`, `s4_rebalance_ranges{state}`, `s4_rebalance_remaining_bytes` and `s4_rebalance_paused{reason}` (`operator`, `no_room`) every 5 s, while the move increments `s4_rebalance_keys_total`, `s4_rebalance_bytes_total` and `s4_rebalance_errors_total{reason}` where it works. A pause is the pool's: `POST /api/admin/cluster/rebalance/pause` (optional `reason`) and `…/resume` write `__system__/__s4_pool_generation_v1/<pool>/pause/<epoch>` (`PauseRecord`, through the quorums, newest write wins) and apply it on the node asked; every member's `TransitionDriver` reads the record each poll, before beginning or starting its move, and pauses or resumes its own move (`PoolTransition::apply_pause`, stored as the move's control record in `cluster_meta`, so a move that has not started yet starts paused and a member that was down applies the pause when it returns). The routes answer `409` while the pool does not grow and `503` when the record could not be written.
  A node with no generation learns the current ordered prefix from existing owners' gossip before building placement; tentative claims of a blank node do not open the gate. Missing or conflicting knowledge refuses startup after a bounded wait rather than inventing a ring. On the first upgrade to protocol 9 a remembered pool must keep its old membership until its generation is recorded; the previous peer record knows identities but not order, so exact order is protected from that first generation onwards. A saved owner can restart without the appended members. A new coordinator inherits identical settled bucket metadata placement from the old owners, waiting while their earlier RF move finishes; that move's driver still considers the old roster. IAM catch-up copies quorum-confirmed control records and tombstones to the learner without counting it as an owner. A new EC node without a roster cache returns an explicit waiting error on a missing or unavailable roster from the old quorum instead of inventing an empty list; old owners retain the inherited-set semantics. The generation record survives an opening in single mode.
- **Stable Member Identity**: Bootstrap passes each pool's resolved NodeId roster directly to placement; addresses are transport hints and may be reused without merging two identities. Duplicate identities are rejected. The remembered peer record is persisted with file fsync, atomic rename and directory fsync.
- **Quorum (N=3, W=2, R=2)**: Reads and writes tolerate 1 node failure. W+R > N guarantees read-your-writes.
- **Replication Classes**: The placement decision of a key (`PlacementRouter::route`) carries its replicas and the quorums of its class (`ReplicationClass`: `BucketMetadata` for a bucket's marker and its six configurations in `__system__`, `ClusterControl` for the IAM records of version 2, `__system__/__s4_iam_v2_*`, `Data` for everything else), taken from the pool's `PoolLayout`. `ClusterControl` is on every node of the pool, written and read through a majority (`⌊N/2⌋ + 1`, `ClassLayout::majority_of`), so two majorities always meet; the coordinators send its writes, deletes and reads only to nodes that announced protocol 8 (`IAM_REPLICATION_MIN_PROTOCOL_VERSION`, `coordinator::takes_class`) — a node of an earlier release would keep such a key without a digest — and a node that announced none yet is sent them. The read and write coordinators, read repair, hinted handoff (through the coordinators), tombstone GC and the scrubber take replicas and quorums from there and nowhere else; anti-entropy pairs nodes on the pool's data ring, and the bucket metadata of a moving pool by their own layout. Bucket metadata are placed like the data unless the pool moves them. **Bucket metadata target and stages** (`s4-cluster/src/metadata_placement/`, run by `s4-server/src/bucket_metadata_placement.rs`): at start a node derives the shape its pool's bucket metadata is to reach (`derive_target`): `RF_meta = min(N, max(RF, 2f + 1))` with majority quorums, where `f` is `min(RF − W, RF − R)` for a replicated pool and, for an erasure-coded one, the shard losses every erasure set decodes past whichever they are (`LossTolerance::guaranteed_losses` in `ee/s4-codec`, put to the decoder pattern by pattern: 2 for RS 4+2 and LRC 4+2+1, 3 for RS 6+3, RS 8+3 and the larger LRC profiles); a target equal to the data's replication factor keeps the data's quorums. `S4_BUCKET_METADATA_REPLICATION_FACTOR` may raise it up to `N`; below the derived value or above `N` the start is refused. The node keeps where it is in the move — from which shape to which, the stage (0 `Legacy`, 1 `DualWrite`, 2 `ReadNew`, 3 `Settled`; `Stage::rules` is the one table of what each stage writes to and reads from) and whether its backfill finished — as a record in `cluster_meta` (`bucket_metadata_placement`, kept by an open without digests, stored only if it follows the stored one: a stage never goes back), and announces it in gossip as the second part of the metadata tail, after the adoption flag, so that a protocol 6 node reads its own part and stops. A node with no record starts the move from the data's shape, or is settled at once when there is nothing to move (every replicated pool of RF 3, W = R = 2); a stored move goes on to its own end before a new target is taken, and fewer replicas than the pool holds are refused with a warning, the record kept. Every second the node puts its gossip view to the gate of the next stage (`next_stage`): every node of the pool's list alive, at the protocol of the move (`BUCKET_METADATA_MIN_PROTOCOL_VERSION`, 7), announcing the same move at the current stage or later, and before stage 2 every backfill finished; the new stage is stored before it is announced. An exhaustive check over a pool of six nodes proves that the rules of two neighbouring stages meet — every set of acknowledgements a write accepts meets every set of answers a read decides on — for 3 → 5 replicas on one ring and for replicas moved on a grown ring, and finds the write a read misses for stages two or three apart. **Stages in traffic** (protocol 7): while the pool moves its bucket metadata, the router places their keys by this node's stage (`BucketMetadataMove::place`): the decision carries the nodes a write goes to (both layouts at stages 1 and 2, the old one first), the nodes and quorum a read takes (the old layout at stages 0 and 1, the new one at 2 and 3) and the write rule (`WriteRule`: every requirement met by the replicas that acknowledged — at stages 1 and 2 the old write quorum among the old replicas and the new one among the new). The write coordinator waits until the rule holds and names the first requirement unmet in `QuorumNotMet`; a key of the data, or of a pool that moves nothing, has one requirement, as before. Every such decision holds a ticket of its stage (`StageCell`, `StageTicket`) for as long as the write runs; a change of stage takes the new stage for the writes that begin after it at once, and the driver stores and announces it only once the writes of the previous stage ended. Writes and deletes carry the stage they were placed by (`bucket_metadata_stage`) and whether they are a repair copy (`repair_copy`: read repair, reconcile — anti-entropy, hints, adoption — and hint replay); a replica of a moving pool at stage `s` refuses a client's write of bucket metadata placed by a stage below `s − 1` (`Stage::fences`, `stage_fenced` in the answer, no hint for it), so a node of an earlier release, which sends 0, writes no bucket metadata from stage 2 on; a pool that moves nothing fences nothing. **Backfill, anti-entropy and GC of a move** (`metadata_placement/{backfill,driver}.rs`): the driver of the stages (`StageDriver`, run by `s4-server` on gossip) runs at stage 1, once every node of the pool announced stage 1, backfill passes over the bucket metadata of the node's own version digests, tombstones included: each key is settled on every replica of both layouts (`Reconciler::settle_counting`, every replica required). A copy is spread only when the old layout confirms it — the replicas whose copies count are those of the layout reads take (`KeyVersions::confirming_replicas`), so at stage 1 a copy needs the old write quorum among the old replicas, or tombstone horizons older than it on every replica without the key; a copy short of that is a write that failed, left as it is and counted `unconfirmed`. A tombstone is carried to every replica. Before a marker is settled, every copy of it outside the old layout that its node made up (no HLC of its own, or one of node 0) is removed, exactly that generation (`Reconciler::remove_made_up`), whichever node settles the key first: an earlier release made a marker up on a node taking a write into a bucket it held no marker of, stamped by its modification time, which ranks above the real marker or outlives a delete that left no tombstone — harmless while only the old layout is read, wrong once that node is a replica; such copies are counted `dropped`. A pass in which every key settled is stored and announced as the finished backfill, which the gate of stage 2 waits for on every node; another pass follows a failed one. Anti-entropy compares the bucket metadata by the scope the round's caller chose and sends (`BucketMetadataScope` in the leaves and keys requests): the old layout at stage 0, left out at stages 1 and 2, the new layout once settled; the peer answers by that scope whatever its own stage, so the leaves of neighbouring stages match, and a caller of an earlier release, which sends none, is answered like the data. Tombstone GC keeps the tombstones of bucket metadata at stages 1 and 2, and once settled removes one only when the cut of every other replica is also past the moment this node took stage 3 (`PoolLayout::tombstone_keep`, `StageCell::settled_since`): only rounds begun since compared the key on its new replicas. An erasure-coded pool of six nodes moves from three replicas to five by itself and then confirms every bucket with any two nodes down. **Observability** (`metadata_placement/status.rs`): the driver writes where it stands to a `PlacementStatus` — the record and the nodes the next stage waits for — which sets `s4_bucket_metadata_stage{pool}` and `s4_bucket_metadata_replication_factor{pool}` (the target) in the same call and which `/cluster/health` answers from as `bucket_metadata` (stage, `from`, `to`, `backfill_complete`, `held_by` with each node's name and reason, `held_for_secs`); a gate that holds ten minutes is warned about once every ten minutes with that list (`HOLD_WARN_INTERVAL`). Each backfill pass counts its keys in `s4_bucket_metadata_backfill_keys_total{outcome}` and itself in `s4_bucket_metadata_backfill_passes_total{outcome}`; each fenced write in `s4_bucket_metadata_fenced_writes_total`.
- **Read Failure Semantics**: Only an explicit `ObjectNotFound` counts as an absence response; storage failures remain errors in local digest collection and replica HEAD/read handlers, and a replica's HEAD answer that carries an error is an error to the coordinator even though it says the key does not exist. The digest collector owns its replica futures directly, so cancellation aborts pending async reads rather than detaching them. The brief late-response drain cannot extend the digest quorum deadline; this is not a deadline for the subsequent object-body transfer or already-started blocking disk I/O.
- **SWIM Gossip**: Failure detection via the `foca` crate: a member foca has suspected for 5 s is reported down and S4 marks it `Dead`. foca's suspicion is not surfaced, and a stopping node does not announce leaving, so `Suspect` and `Left` are not set today. foca tracks members by address, so one node id appears twice across a restart that changes address — at the address the node left and at the one it answers on. Membership is therefore kept per identity: a death notice applies only to the run a node is currently known by, a rename records whoever took over an address and forgets where the displaced node is rather than calling it dead, and a changed address drops the metadata that described the old endpoint. Node metadata is ordered by process start time and then broadcast counter, so a restarted node's broadcasts are not mistaken for stale ones by peers that stayed up. The gRPC pool re-checks a peer's address on every call and drops a cached connection to an address the node has left. A clock that moves backwards across a restart still makes the returning run look older, in gossip as in foca itself. A member declared dead is not left believing it is still one: the peer that drops its messages tells it so (foca's `notify_down_members`), and it rejoins under a renewed incarnation. Every node also announces itself each second to the seeds it does not see alive, so a node that was paused past the suspicion timeout, and both sides of a healed network split, rejoin without a restart.
- **gRPC Inter-Node**: Data and metadata replication over gRPC (port 9100), optional TLS. The node binds the port before it goes on starting (`NodeRpcServer::start`, `SO_REUSEADDR`, so connections of an earlier run in `TIME_WAIT` do not hold it): a port another process holds stops the start with an error instead of leaving a node its peers cannot reach. A blob body at or above 8 MB is replicated through `WriteBlobStream` in 256 KB chunks instead of one message, so an object larger than the 16 MB message limit still reaches quorum; the replica reassembles it and commits it through the same durable write path as a unary `WriteBlob`. A peer that does not serve the streaming method answers `Unimplemented` and the write falls back to unary, so a mixed-version pool keeps working.
- **Multipart Quorum State**: Multipart sessions, uploaded part records, and completion are stored through the replica quorum, so load balancers do not need sticky sessions. `UploadPart`, `UploadPartCopy`, and aws-chunked multipart requests stream through bounded buffers instead of materializing full parts in RAM.
- **Bucket-to-Pool Pinning**: Each bucket belongs to one pool. All objects in a bucket are on the same set of nodes.
- **Tombstones**: In a pool of more than one replica a delete of a user bucket's key, of a bucket marker or of a bucket configuration leaves a tombstone rather than removing the key: a record of the objects (or buckets) keyspace with `is_delete_marker`, no version ID, no data and the HLC of the delete (`StorageEngine::tombstone_object`). The IAM records of version 2 leave a tombstone too. The rest of `__system__` — the IAM records of earlier releases, erasure-coding metadata — is deleted as before (`is_replicated_key` in `s4-core/src/types/metadata.rs`, the same rule that decides which keys have a version digest): erasure coding removes its metadata at the HLC of the very generation it removes, which a tombstone at that HLC would leave in place. It is ordered against writes of the key by the same last-writer-wins rule (`IndexRecord::keeps_over`, by `VersionRank`, see HLC Ordering) — a write older than the delete does not come back, a newer one replaces the tombstone, a write of the very same HLC gives way to it, and so for a multipart completion — and a key the replica never held gets one too. The replaced record's data is released in the same batch, and the tombstone is journalled as the record it is. A versioned delete marker lives under `key#version_id` and is no tombstone. Every read path of the storage engine answers a tombstone as an absent object, and a listing skips it while filling its page; `key_version` and `list_objects_with_tombstones` are what tell a tombstone apart. Replicas report it as a version: HEAD and read answer `tombstone` with the delete's HLC, and a listing includes tombstones on `include_tombstones`. A quorum read decides on the newest version among the answers (`decide` in `s4-cluster/src/coordinator/read.rs`): an object is served once R replicas hold a version, while a tombstone, or no version at all, is "not found" once R replicas answered at all. The distributed listing merges every node's entries by `VersionRank`, tombstones included, hides a key whose newest version is a tombstone, answers only while no more than `RF − R` nodes of the pool are silent — then every key has a read quorum of replicas answering, one holding its last acknowledged version — and is `QuorumNotMet` (`503`) otherwise, rather than drop an object or show a deleted one, and scatters again past a node's batch until the page holds its objects — after 16 batches the page is returned short and truncated, with a token past the last key scanned, empty if those batches held only tombstones, so one request never scans without bound. If a live candidate lacks R holders in those separate snapshots, LIST confirms that key through the same quorum metadata read as HEAD, bounded by the original scatter deadline: a confirmed version supplies its current metadata, a confirmed delete removes the candidate and the page continues filling, and an unconfirmed legacy copy still fails. Only QuorumNotMet is retried, with bounded backoff and fresh placement, within that same deadline; a PUT still reaching its quorum can finish while the listing waits. This confirmation counts as part of LIST rather than an extra client HEAD. Only a page that is not truncated means there are no more keys; the callers that need the first keys whatever lies before them — the emptiness check of DeleteBucket, ListBuckets, the EC tiering bucket sweep — follow the pages (`DistributedListCoordinator::list_up_to`). A node's scan after a token starts right past it rather than at the start of the prefix. A purge of one generation by `expected_source_hlc` stays a physical delete, and a pool of one replica deletes as before. Nodes advertise tombstones with protocol 4 (`TOMBSTONE_MIN_PROTOCOL_VERSION`): a client's delete reaches every replica as it always did, but a delete repaired onto a replica after the fact goes as a tombstone only to a node at protocol 4 or above, and to an older one as the delete of exactly its stale generation. On a cluster node the lifecycle worker expires an object with a tombstone stamped by the node's clock, and only the generation it evaluated. A replica that takes a write into a bucket whose marker it holds as a tombstone does not make the marker up again; one that has never seen the marker makes it up with the oldest HLC there is (wall 1, node 0), so any marker CreateBucket writes and any tombstone DeleteBucket leaves outvotes it. `s4-server --purge-tombstones`, run on a stopped node, removes every tombstone from its data directory before a release from before tombstones opens it.
- **Hinted Handoff**: A replica whose write or delete fails, times out or is skipped as dead gets a hint from the coordinating node, decided by that replica's own outcome: one that answers after the client has its quorum gets none, and a node never hints itself. A hint names the bucket, the key and the HLC of the missed operation, not the object; a purge of one generation's hot copy keeps that generation. Hints are appended to one log per target, in segments of records with a length and a CRC32, stores that arrive together sharing one fsync; a target's log is capped at 1 GB, and a segment is removed once its newest hint is older than `S4_HINT_TTL_HOURS`. Every 30 s the maintenance loop closes the open segments of the targets gossip holds alive and delivers the closed ones: for each hint it reads the newest version of the key, a tombstone included, from every other replica (`KeyStateSource`, implemented by the read coordinator without a quorum operation or read repair) and brings the target to it with the code anti-entropy settles keys with (`Reconciler::bring` in `s4-cluster/src/repair/reconcile.rs`) — the copy is written with its own HLC so the target's LWW keeps anything newer; a tombstone is sent as a delete at its HLC to a target at protocol 4 or above, which keeps it as its own; a target record with a made-up HLC no newer than the tombstone gives way to the tombstone, and one newer is left alone; a target older than protocol 4 loses its record only if that is no newer than the tombstone and only by that record's exact HLC (sent only to nodes at protocol 2 or above, which understand `expected_source_hlc`); a key no other replica holds is removed from the target the same way when the missed operation was a write; and an erasure-coded key is `superseded`. A delete hint treats a copy older than the delete, or no version at all, as the delete itself being the newest version. A replica before protocol 4 that took a delete has no key, so when such a replica lacks the key a copy is written only if as many of the other replicas hold it as a confirmed write leaves (`min(W, RF − 1)`); otherwise it may have missed a delete, nothing is written, and the hint is `ambiguous` unless the target already holds that version or a newer one, its own tombstone included. A replica at protocol 4 or above that lacks the key took no delete since its tombstone horizon, which it reports with the absence: it does not hold back a copy newer than that horizon, and holds back one as old or older like a replica before tombstones. A hint whose key cannot be settled now — another replica down or not answering, or a write hint younger than the replica write timeout whose write the others do not show yet — is carried over, with its age, into a new segment and the pass goes on; a segment is counted and removed once each of its hints is settled or carried over, and one in which nothing but expired hints could be settled is left as it is, so a long second outage does not get it rewritten every pass. Only a target that stops answering ends the pass over its hints. A key deleted between the read and the write to the target does not come back there: the target took the delete as a tombstone newer than the copy, and its LWW refuses the copy — on a target at protocol 4 or above.
- **EC Small-Placement Hints**: A separate durable continuation covers the whole placement-debt queue. Retry updates use snapshot comparison; acknowledgements and deletes clear only the placement generation they cover. These local hints are not a substitute for quorum-durable placement facts in the original data write.
- **Read Repair**: A read serves only the newest version: when no replica of it can hand its bytes over, the read fails rather than serve an older copy. Stale replicas are asynchronously updated when a full quorum read (`QuorumReadCoordinator::read`, used by CopyObject and EC internals) detects them: a replica older than the newest object gets its copy, a tombstone older than it included, and a replica whose copy is older than the newest tombstone is brought to the delete — as a tombstone on a node at protocol 4 or above, as the delete of exactly its stale generation on a node at protocol 2 or 3, not at all on an older one. During a pool-generation move the targets also include owners of the other generation that were not asked for the read; HEAD and streaming GET then schedule a full-object fetch from the selected source, fenced by its HLC and ETag. The worker transfers it in bounded chunks to a remote target and applies the same LWW replica handler locally. Tombstones are repaired to both generations by the same rule. An erasure-coded record is left to the EC runtime.
- **Buckets**: A bucket exists while its marker `__system__/__s4_bucket_marker_<bucket>` does, and the marker goes through the quorums like any object: CreateBucket and DeleteBucket (S3 and admin API, `create_bucket_marker` and `delete_bucket_and_contents` in `s4-api/src/handlers/bucket.rs`) change it through the write quorum, and every request that writes to, lists or deletes from a bucket reads it through the read quorum first (`check_bucket_cluster`), before the storage lock is taken. A read of one object asks only when the object is not found (`object_not_found`). DeleteObjects deletes each key through the write quorum, as DeleteObject does (`delete_object_in_cluster`). The admin API's bucket statistics and object listing and the counters of `/api/stats` read the pool, not the node (`s4-api/src/handlers/usage.rs`): every node's listing merged by key, page by page, with `complete: false` when a node did not answer. The pool's usage is reused for 10 s and counted once for all concurrent requests, since `/api/stats` is open; creating or deleting a bucket through the node drops it. The deduplication numbers of `/api/stats` stay the node's own.
- **Versioning and Object Lock**: Not supported in cluster mode, where objects are written and deleted through the quorums without versions or retention checks. Every request that would turn either on answers `501 NotImplemented` before anything is read or written (`s4-api/src/handlers/cluster_unsupported.rs`): PutBucketVersioning, PutObjectLockConfiguration, CreateBucket with Object Lock, PutObject, CopyObject and CreateMultipartUpload with `x-amz-object-lock-*` headers, and object retention and legal hold. GetBucketVersioning answers unversioned and GetObjectLockConfiguration not found. Configurations an earlier release accepted stay on the node that took them; `s4-server/src/unenforced_configs.rs` warns about each at start and keeps `s4_bucket_unenforced_configs{kind}` current, and `/cluster/health` lists them as `unenforced_bucket_configs`.
- **HTTP liveness and readiness:** `/health` and `/minio/health/live` report that HTTP is alive. `/minio/health/ready` reports this node's local recovery: 503 with `Retry-After: 1` and a fixed, non-sensitive `X-S4-Readiness` reason until local bucket configuration adoption, migration of records from single mode, IAM adoption and the initial IAM freshness check have completed; stale IAM freshness also makes it 503. A successful durable configuration completion is required; an ambiguous deletion history stays Pending until it can be confirmed, without a timeout that declares success. Readiness reads in-memory status and starts no RPC or storage scan. The protected cluster health exposes `bucket_config_adoption` (phase, pending count and bounded reason samples). Single and gateway mode retain their existing readiness. The supplied HAProxy deployment loads an initial DOWN state for every backend before accepting requests, resolves addresses from configuration rather than from that state, and promotes backends only through successful readiness checks. HAProxy and Kubernetes readiness probes use `/minio/health/ready`; liveness probes use `/health` or `/minio/health/live`. A degraded pool alone does not make a locally recovered node unready. Gossip, replica RPC, metrics and diagnostic Admin API remain reachable while HTTP readiness is 503; membership, placement and quorum votes are unchanged. A single-to-cluster cutover requires every intended client backend ready and the source's migration pending count zero.
- **Bucket configurations**: The six keys of a bucket's configuration (`__system__/__s4_bucket_{cors,versioning,lifecycle,policy,object_lock,encryption}_<bucket>`, `BUCKET_CONFIG_KEY_PREFIXES` in `s4-core/src/types/metadata.rs`) are replicated keys since protocol 6: placed with the bucket markers, with a version digest, a tombstone for a delete, anti-entropy and tombstone GC. DeleteBucket deletes all six through the write quorum and so leaves a tombstone of each, and a configuration write that missed the delete does not bring it back. In cluster mode the S3 handlers of CORS, lifecycle, policy and encryption go through the quorums (`read_bucket_config`, `write_bucket_config`, `delete_bucket_config` in `s4-api/src/handlers/bucket_config.rs`): Put and Delete check the bucket through a read quorum and then write or delete the key through the write quorum; Get reads the marker and the key through read quorums, side by side, and a configuration counts only when it belongs to the live marker's generation — an older one belongs to an earlier bucket of the same name and reads as not set (`config_of_generation` and `QuorumReadCoordinator::read_bucket_config` in `s4-cluster/src/coordinator/bucket_config.rs`, which the lifecycle worker reads its rules through too). A configuration with an HLC a node issued belongs when it is newer than the marker; one with a made-up HLC — stored before protocol 6, ordered by the wall clock of the node that stored it, while the marker's HLC came from another node — when its wall time plus `LEGACY_CONFIG_CLOCK_TOLERANCE` reaches the marker's, so that a configuration written right after CreateBucket through a node whose clock runs behind is not lost. The tolerance is the clock skew the cluster tolerates anyway (`MAX_CLOCK_SKEW`, 500 ms): within it the clocks cannot tell such a configuration from one of an earlier bucket deleted and created again as fast — the previous release, without tombstones, left that one on a node that is no replica of its key and served it to the new bucket too — so the new bucket gets it, and adoption logs a warning for every configuration taken by the tolerance (`within_clock_tolerance`). The configuration is newer than the marker of its own bucket by causality, not by clocks: the bucket check moved the node's clock past the marker (`clock.observe`, the single-node read bypass included), and the write takes a later HLC. CreateBucket reads the six keys through read quorums before it writes the marker, so the new marker is newer than any configuration a write that raced the previous DeleteBucket left — even one stamped by a node whose clock runs ahead. Too few replicas answering is `503`. **Adoption:** before protocol 6 a configuration was stored only on the node that took it, without an HLC, and that node is often not a replica of its key, which anti-entropy never compares. At every start until it finished, a node passes over its configurations with a made-up HLC (`ConfigAdoption` in `s4-cluster/src/repair/config_adoption.rs`, run by `s4-server/src/config_adoption.rs`, retried when relevant peer membership, identity, protocol, placement or generation changes, with at least 1 s between pass starts and a 30 s fallback while keys are left): every replica of the key has to answer; a replica holding a version of a higher rank, a delete included, keeps it (of two values the one changed last wins); a configuration whose bucket has no live marker of its generation is not spread, and that generation and older ones leave every replica holding them (`Reconciler::remove_stale`), this node's own copy included; otherwise the copy goes, with its made-up HLC, to every replica behind it without counting holders (`Reconciler::deliver_copy`) — unless the copy changed since it was listed, which leaves the key for a later pass — and a node that is not a replica of the key then removes exactly that generation of its own copy, physically. A complete pass must be successfully recorded in `cluster_meta` (`bucket_configs_adopted`, dropped by an open without digests or without a trusted shutdown seal) before the local `ConfigAdoptionStatus` becomes Ready and it is announced in gossip (`GossipHandle::announce_bucket_configs_adopted`); a failed durable completion remains Pending and is retried. The announcement is a tail (`MetaTail`) after the postcard-encoded `MetaBroadcast` rather than a field of `NodeMeta`, so that a protocol 5 node, whose `postcard::from_bytes` stops at the end of `MetaBroadcast`, still reads the broadcast, foca relays the tail with it, and a broadcast without one reads as not adopted. **Gate:** a node reads configurations through the quorums only once every node of its pool announced its adoption and gossip holds it alive with protocol 6 or newer (`open_gate` in `s4-server/src/config_adoption.rs`, which looks at this node's gossip view every second and sends no request to a peer; `AppState::config_read_gate`). An open gate is recorded in `cluster_meta` (`bucket_config_quorum_reads`) and survives uncertain restarts and opens without digests. A separate permanent history marker (`bucket_config_history_requires_confirmation`) is set when adoption completes, quorum reads open, or existing configuration history becomes uncertain. Either marker opens the gate at startup (`initial_gate`), and repeated adoption requires confirmation of the owners' deletion history before spreading a foreign copy; a missing guarantee leaves it pending. Thus a crash or a restart while a peer is down cannot reopen local fallback. Only during initial legacy adoption, with neither marker set, GetBucketX and the lifecycle worker weigh the configuration this node holds itself too (`read_bucket_config_with_own`): it is the answer when it belongs to the marker's generation and no replica of the key that answered holds a version of a higher rank — a newer value or its delete (`key_versions`); otherwise the quorums answer, so a node whose copy adoption moved to the replicas still reads it. Writes already go through the quorums. `s4_bucket_config_quorum_reads` is 1 once the gate is open, and `s4_bucket_config_adoption_keys_total{outcome=adopted|superseded|orphaned|deferred}` counts every pass. The count of unenforced versioning and Object Lock configurations (`s4_bucket_unenforced_configs`, the `unenforced_bucket_configs` of `/cluster/health`) is taken after each pass of adoption and every 10 minutes (`s4-server/src/unenforced_configs.rs`), and health answers from the last count rather than scanning the storage. **Lifecycle:** a node holds objects of buckets whose marker it does not hold, so the lifecycle worker of a cluster node (`with_cluster_buckets` in `s4-server/src/lifecycle_worker.rs`) takes the buckets from the distributed listing of their markers, page by page and without a cap, and each bucket's rules through `read_bucket_config_with_own` — before the gate its own rules weighed too, as GetBucketX — and expires its own copies of the objects as before; a rule that cannot be read through the quorums skips its bucket until the next evaluation. It evaluates every bucket as unversioned: cluster mode keeps no versions, whatever versioning setting a node stored before it refused it.
- **Erasure-coded pools, small objects and their errors** (EE): an object below the profile's
  `min_object_size` stays on its three hot replicas, and its replicated-small placement — replicas,
  size, SHA-256 and the version it was recorded for — is written to those replicas with every version:
  the write is an operation of that version (`small_placement_write_kind`), since a replica takes a
  repeated operation for a retry and would keep the placement of the version before, and a read of the
  placement takes the newest one answered. A GET whose HEAD found hot copies that were moved into the set before the read (every replica
  answers with an erasure-coded entry, `ClusterError::ErasureCodedOnly`) reads the object through the
  set. A read or HEAD whose hot copies hold a version newer than
  the placement it met — an overwrite this node's cached layout, or a replica the overwrite missed,
  still describes as the version before — reads the object as a hot one and drops the cached layout
  (`ReplicatedSmallSuperseded`), rather than refuse the new bytes as the wrong size. A tombstone
  manifest closes the versions before it, not a write made since: a key written again after its delete,
  whose hot copies hold a version newer than the tombstone, is read — and deleted again — as an object
  with no manifest, and the node drops the tombstone it kept (`hot_replicated_newer_than`). An S3 DELETE
  must first commit its namespace tombstone through the ordinary RF=3/W=2 quorum, even after hot bytes
  were purged, and then pass that delete's HLC and operation ID to the EC runtime. A cached EC HEAD
  does not prove namespace quorum availability; a failed namespace delete returns 503 without an EC
  delete commit. A queued repair whose matching manifest is quorum-confirmed `Promoted` finishes
  as obsolete, without shard I/O, repair-frontier advancement or repaired-byte metrics. A local
  cached promotion alone cannot complete the task; an unavailable quorum keeps it retryable.
  A manifest write or removal returns once the manifest quorum
  acknowledged it and lets the requests still in flight finish, so every node that answers converges
  on the new state — a node left behind with the old one, and one of those that acknowledged then
  restarting, would split the set so that no state reaches the quorum a read needs. A manifest read
  whose set reaches no verdict — a manifest written, removed or moved to its next state at that
  moment is on some nodes and not yet on others, and with a node of the set down neither side reaches
  the manifest quorum — asks the set again up to three more times, 50, 100 and 200 ms apart
  (`read_until_decided`), before it gives up. A metadata read of the pool that reaches no quorum —
  nodes just back from a restart, or down — is `ClusterError::Unavailable` and answers `503`, a retry
  for the client, never `500`.
- **HLC Ordering**: Hybrid Logical Clocks provide causal ordering; conflicts resolved by Last-Writer-Wins (LWW). Every place that weighs two versions of a key — the storage's LWW (`IndexRecord::keeps_over`), the quorum read, the listing, anti-entropy and hint delivery — weighs them by one total order, `VersionRank` (`s4-core/src/storage/version_digest.rs`): the HLC first; at one HLC an object gives way to its erasure-coded entry and both to a tombstone; between objects of one HLC the ETag — one of the multipart form (`<hex>-<parts>`) above any other, since only a completed upload gives one and a copy stored without its source's ETag carries the MD5 of its bytes, then the greater BLAKE3 of the ETag. Two replicas hold the same version exactly when their ranks are equal, which is what the version digest records, and an incoming version is stored only when it ranks strictly higher: because the order is total and the same on every node, replicas reach one version from any state and in any order of deliveries, and a repeated delivery changes nothing. A client's write or delete that a replica turns away because it holds a newer version — the coordinator's clock is behind the one that issued that version — is not lost: the replica answers success with the HLC of that version (`superseded_by`), and the coordinator observes it and sends the operation once more with an HLC above it (`write`, `delete`; as CockroachDB raises a write that meets a newer one). With 2W > N a version confirmed to a client before the operation began is on a replica that answers, so the raised operation lands above it; a version newer still is a concurrent operation, and the raised one is not raised again. A multipart completion cannot be sent again once a replica closed its upload, so the inspection before it reports the key's version on each replica (`key_hlc`) and the completion is issued above all of them. The erasure-coding garbage collector deletes the replicated copy of a deleted object with `delete_once`, which is never raised: the version that outranks it is a client's write made since. A record written without an HLC is ordered by its modification time with node 0 (`IndexRecord::reported_hlc`, `HlcTimestamp::of_record`) on every read path, node, listing and version digest, and read repair and hinted handoff keep that made-up HLC on the copies they write, so `is_made_up` still tells them apart. Hinted handoff writes a made-up copy only after a HEAD shows the target holds nothing newer, because the target's LWW does not weigh its own record without an HLC; it removes a target's record with a made-up HLC no newer than the missed delete by that HLC (a repaired copy) or by the zero HLC (a record that stores none, and only such a record), checking with a second HEAD whether the record went, since the replica answers a conditional delete the same way either way. On a cluster node a conditional delete checks the generation and deletes under one write lock of the shared storage (`SharedStorageAdapter::delete_object_if_hlc`), so a write that lands meanwhile is never deleted unchecked.
- **Listing confirmation**: Like GET/HEAD, a client LIST returns a live key only when its current read owners hold at least R versions of it (different versions count; absence does not). Otherwise it returns `503`, even if every node answered: a pre-tombstone DELETE could leave a lone stale copy. The scatter records distinct holders without extra RPCs; tombstones still hide live copies, pagination excludes unscanned keys, and the explicitly incomplete administrative `list_answered` keeps its reporting behavior.
- **Anti-Entropy**: On a cluster node the index keeps a version digest of every replicated key — the keys of user buckets, the bucket markers, the bucket configurations (`BUCKET_CONFIG_KEY_PREFIXES`) and the IAM records of version 2 (kept in the index's `iam` keyspace, which has digests since format 5), not the rest of `__system__` and not versioned records — in the `version_digests` keyspace (`s4-core/src/storage/version_digest.rs`): the HLC, origin node, ETag hash and kind (live, tombstone, erasure coded) of the version the key holds, keyed by the key's ring position and then the key, so that the keys of a ring range are one scan. The ETag and not the content hash, because the content hash describes how a replica stores the bytes: a multipart object holds none, while its copy repaired onto another replica is one blob with a hash of its own. Whoever writes such a copy — anti-entropy, hint delivery, read repair — sends the source's ETag in its own field of the write (`WriteBlobRequest.etag`), never in the metadata: the replica drops a metadata key `_s4_etag` (`REPAIRED_ETAG_METADATA_KEY`) that arrives, and hands the field to the storage under that key only together with an HLC; the storage keeps it as the record's ETag only for a write that carries an HLC. A node that predates the field computes the ETag of the bytes, and its copy is a version of a lower rank that a round puts right once it is upgraded. The HTTP layer drops every user metadata key starting with `_s4_`, and CopyObject does not copy them from the source's stored metadata (the physical storage class aside), so a client sets neither an ETag nor an HLC. The ring position is the hash placement places keys by, defined once in `s4-core` (`ring_position`). `IndexDb` changes a key's digest in the same atomic batch as its record, in `batch_write`, `put` and `delete`, so no write path of the engine goes around it; a restore rebuilds the digests, and where the data sits is not part of a digest, so compaction leaves it alone. The node opens its storage with digests (`IndexOptions::version_digests`) before it serves anything, and trusts them only when the `cluster_meta` keyspace holds their current layout version (5: a record without an HLC described by its made-up one, the bucket configurations and the IAM records of version 2 included) and their keyspace exists, with a readable seal beside the database that records its current fjall sequence number. A missing, unreadable, malformed or outdated seal cannot distinguish a crash from writes by an earlier release that kept no digests or tombstones: before rebuilding, the index atomically moves its settled tombstone horizon to a retained lower bound, forgets the born-with-digests marker and resets completion of bucket configuration and IAM adoption. The purge horizon, pool generation, placement, rebalance progress and the monotone switch to quorum reads of bucket configurations remain. A separate monotone configuration-history marker also survives older builds erasing their adoption flags. It is set by local adoption, the pool cutover, or an uncertain restart with existing configuration digests; the first adoption from a legacy index without digests, or from digest formats 1–3 without earlier adoption, may still trust a lone local copy. Either marker disables local fallback: after uncertain history, repeated configuration adoption requires enough current owners holding the copy or every absent owner reporting a horizon older than it; ambiguous foreign copies remain pending instead of resurrecting collected deletes. A graceful stop seals the database only after its writers stop; the sequence number is captured before syncing the database, then the seal file is synced and renamed. Otherwise it rebuilds the digests from the records and logs how many and how long. A storage opened without digests — single mode, `s4-server --purge-tombstones` — drops them, and the next cluster start rebuilds them. On its first cluster start, before the gRPC server, each node also settles its tombstone horizon (`IndexDb::settle_tombstone_horizon`): the HLC from which every delete on it left a tombstone: zero when this start created its index (a marker in `cluster_meta` records an index created with digests, and an open without digests or a restore drops it), otherwise its clock plus the tolerated clock skew, since an emptied index may still have deleted keys without tombstones and a peer's clock may run ahead; later starts with an unchanged readable seal keep it; an uncertain restart settles it to the maximum of its retained lower bound and the current clock plus tolerated skew, and an open without digests drops it, because deletes then leave no tombstones. A replica that holds nothing for a key reports its horizon in the HEAD answer (`tombstone_horizon`). **Rounds** (`AntiEntropyRounds` in `s4-cluster/src/repair/anti_entropy.rs`) run on every node of a replicated pool, one every `S4_ANTI_ENTROPY_INTERVAL_SECS`, each with the next live peer of the pool in an order shuffled at start. A round compares the pair's tree (`s4-cluster/src/repair/pair_tree.rs`): the keys placement gives both nodes (found by the ring arcs both are replicas on, worked out once per round: `ConsistentHashRing::cover_of`; the cluster's control state is on every node, so every pair of the pool compares all of it), cut by the top 14 bits of the ring position into 16 384 leaves, each the XOR of `blake3(full key ‖ digest)` — computed afresh in one pass over the digests, never stored. The peer sends its whole leaf vector (`AntiEntropyLeaves`, 512 KiB), and for the leaves that differ both sides compare keys and digests, the peer's a page of up to 1000 at a time (`AntiEntropyKeys`), one leaf held at a time; a key the two hold in different versions, or one of them only, is divergent. Each divergent key, up to `S4_ANTI_ENTROPY_MAX_KEYS_PER_ROUND`, taken in ring order from just past the last key the previous round with that peer took and around the ring, so that keys that do not settle never keep the rest from their turn, is settled (`Reconciler::settle` in `s4-cluster/src/repair/reconcile.rs`): its version is read from every replica, each given the replica read timeout, the pair's answers required and a replica that does not answer in time listed as such (`KeyStateSource::key_versions`), the version of the highest `VersionRank` is picked, a tombstone included, and every replica that answered and ranks lower is brought to it — a replica whose record went to erasure coding is left to the EC runtime, and the others still are — the copy with its HLC and ETag (chunked over the wire above 8 MiB, the ETag in the stream's header), the tombstone as a delete at its HLC; this node's own replica is reached through its replica handlers, not the network. A copy goes to a replica without the key only when every replica without it reported a horizon older than the copy, or as many replicas hold it as a confirmed write leaves (`min(W, RF − 1)`); otherwise the key is `ambiguous` and nothing is written. A tombstone older than `gc_grace` is not carried to a replica without the key. A round is `complete` when it compared every leaf and settled every divergent key, `incomplete` when the peer stopped answering, a key failed or was ambiguous, or the key limit was reached, and `skipped` while a live node of the pool announced a protocol older than 8 (`IAM_REPLICATION_MIN_PROTOCOL_VERSION`: protocol 5 answers rounds but gives configurations no digest, protocol 7 none to the IAM records of version 2) — a rolling upgrade under way — while the live peer whose turn it is has not announced its protocol yet (it keeps its turn, so rounds visit every peer in turn), or while no peer is alive; a node gossip has not seen, or a dead one, does not hold rounds up. The peer checks the cursor of a key page against the leaves asked about; each divergent key counts once in `s4_anti_entropy_repairs_total{outcome}`, and a round that ran in `s4_anti_entropy_round_duration_seconds`. `S4_ANTI_ENTROPY_ENABLED=false` (on and off spelled `true/1/yes/on`, `false/0/no/off`; anything else stops the start) stops a node from starting rounds — it warns at start and `/cluster/repair-status` says so — but it still answers the rounds of its peers (`AntiEntropyResponder`, served for a replicated pool only) — only those whose requests carry its own digest format (`digests_format`): a node of protocol 5 sends none, its tree is over another set of keys, and its round with an upgraded peer ends `incomplete` instead of settling keys the two do not both replicate. A complete round sets the peer's cut of the repair frontier (`RepairFrontier::advance_peer`, in memory) to the wall time the round started at less the arrival window (`gc::tombstone::arrival_window`: the 60 s replica write timeout and 0.5 s of clock skew): a tombstone the write of its delete brought to this node with an HLC before the cut was there when the round started, so the peer has it; a round that is not complete sets none, and the node itself has no cut. A tombstone that arrived later by repair or hint is not covered, and its holder — first of all the coordinator, which wrote it at its HLC — keeps it until its own cuts are past it. After each round the node reports the repair frontier lag: the age of its oldest cut over the pool's peers, a peer without one counted from the node's start; it never falls below the arrival window. `MerkleTree` remains for the erasure-coding anti-entropy of the Enterprise Edition.
- **Distributed Tombstones**: Tombstone GC (`DistributedGcService` in `s4-cluster/src/gc/service.rs`) runs on every node of a replicated pool, a pass every `S4_TOMBSTONE_GC_INTERVAL_SECS` (6 hours). A pass walks the node's version digests a page at a time and removes a tombstone once it is older than `gc_grace` (`S4_GC_GRACE_SECS`, else `S4_GC_GRACE_DAYS`, 7 days) and the cut of every other replica of its key, by placement at the digest's ring position, is past its HLC (`can_purge_tombstone`); the node itself is not in the condition. Frontier cuts live only in memory: after any restart GC waits for new complete rounds with every other owner of the key. The tombstones of a page go through the storage engine in one batch under the engine's write lock (`StorageEngine::gc_tombstones`), each only if its key still holds that tombstone, with the keys' digests and the raised tombstone purge horizon in the same batch and one sync to disk. The settled tombstone horizon and the purge horizon are monotone. The purge horizon (`IndexDb::tombstone_purge_horizon`, `cluster_meta`) is the newest HLC of a tombstone GC removed; the node reports the later of it and its settled tombstone horizon (`StorageEngine::tombstone_horizon`), so after a purge its absence no longer confirms a copy older than a removed tombstone, and such a copy on fewer than `min(W, RF − 1)` replicas is `ambiguous`. While a replica is down, or with rounds switched off on the node, the tombstones of the keys it shares wait. A node of a replicated pool does not start unless `gc_grace > S4_MAX_REJOIN_DOWNTIME_DAYS + S4_ANTI_ENTROPY_INTERVAL_SECS × (pool nodes − 1) + 60 s replica write timeout + 500 ms`, the sum checked for overflow. A tombstone a node removed while a peer still holds its own is no divergence the rounds act on: a tombstone older than `gc_grace` is not carried to a replica without the key. A pool of erasure-coded objects runs no such GC; its tombstones are the Enterprise runtime's.
- **Cluster Metrics**: One catalog, `METRIC_CATALOG` in `s4-cluster/src/cluster_metrics.rs`, held equal by a test to `scripts/tests/cluster-metrics-catalog.txt`. `register_cluster_metrics` registers every series of a cluster node at zero before any service starts, with a series for each peer of `S4_POOL_NODES`; label order is part of a series' identity to the recorder, so registration lists labels in the order they are recorded with. Membership (`s4_cluster_nodes`, `s4_cluster_peer_up`) is counted over the configured roster and published from the gossip loop after every change of its member map; a configured member gossip has never heard from counts as dead. Every call to a peer is counted in one place, `NodeClient`. Quorum operations carry `origin`: `client` for the ones a request served — the HTTP metrics middleware runs every request inside `on_behalf_of_client`, a task-local scope that `observe_quorum` reads — and `system` for the node's own work outside it (publishing its records, the move of a grown pool, workers, repair); a task spawned from a request is the node's unless it enters the scope itself, as the completion of a multipart upload does. The reference in `docs/06-monitoring/prometheus-metrics.md` and the Grafana dashboard `docs/06-monitoring/grafana/s4-cluster.json` are held to the catalog by `s4-cluster/tests/monitoring_docs.rs`: every metric, label and closed label value they query is one a node exports, and every metric of the catalog is in both.
- **EC Tombstone Sweeps**: Each metadata page fits both the remaining manifest scan budget and the candidate limit. The shared EC metadata pager seeks directly past its cursor with a native fjall range instead of enumerating the prefix again; it retains one lookahead to detect continuation. This bounds record enumeration, not physical I/O inside the LSM. Background continuation is durable; manual GC has independent opaque cursors and explicit round completion. Owner probes and their corrective handoffs share a ten-second network budget per owner-poll invocation. Only `Unimplemented` enables legacy probes; unknown replies never authorize shard release or handoff to that owner.
- **Per-Node Dedup**: Deduplication remains local to each node (no cross-node dedup coordination). Mark-sweep GC replaces ref-count decrement.
- **Bit Rot Protection**: Background scrubber verifies CRC32 checksums across all volumes (full scan every 30 days). Corrupted blobs are auto-healed from replicas.
- **Deployment Modes**: `single` (default), `cluster` (storage + replication), `gateway` (stateless router).
- **Single-to-cluster migration** (`s4-cluster/src/migration.rs`): a node restarted in a replicated pool hands its unversioned user records without a stored HLC and its bucket markers to every current owner, markers first. Before replica RPCs or background writers start, a paged scan saves the original snapshots as durable obligations in `cluster_meta`; these remain pending if a client overwrites or deletes a source record before every owner is current. Copies keep the source's made-up HLC (`HlcTimestamp::of_record`, node 0), ETag including multipart ETags, content type and persistent metadata. The source reads large bodies with bounded buffers and sends chunks; the existing replica RPC buffers an incoming body. Settling a remote-only newer client version uses ordinary repair and buffers that body on the migration node too. Every attempt uses the existing version order and history confirmation: a foreign source is a holder and never a confirming owner, and a lone old copy is left pending after a collected delete or uncertain absent-owner history. A concurrent client write or tombstone is settled on every owner before its obligation completes. The source then stamps only the unchanged legacy snapshot, or removes the exact confirmed generation when it is foreign, under its shared storage write lock. Completion requires both the queue and the legacy scan empty; its marker avoids scans on later starts with a trusted digest seal. Opening without digests, restore or an uncertain seal invalidates completion. The explicit single-server startup mark is separate from maintenance opens, so the preflight can refuse Enabled/Suspended versioning and an EC destination with single data before identity creation, digest rebuild or adoption while preserving existing cluster upgrade handling. Migration begins once every configured member is alive at the same S4 version and protocol; later unavailable owners delay only their keys, and a moving pool generation delays migration until placement is stable. `S4_CLUSTER_MIGRATION_CONCURRENCY` defaults to 4. `s4_cluster_migration_pending_records` and the health's `migration_pending_records` count remaining obligations; `s4_cluster_migration_records_total{outcome}` counts `migrated` and `superseded` records in this process, with every series registered at zero. Bucket configuration and IAM adoption remain separate. One populated single source is supported; open multipart uploads and version history are not migrated. Operators wait for zero pending on every node before switching clients. The acceptance scenario is 57.
- **Graceful Operations**: On SIGTERM a node finishes the HTTP requests in flight and exits; `/node/drain` answers `501`. Rolling upgrades with protocol versioning. The cluster routes of the admin API (`/cluster/health`, `/cluster/topology`, `/node/health`, `/cluster/repair-status`, `/cluster/rebalance`, `/scrubber/status`) read the state the node's metrics are written from, through `ClusterAdminService` (`s4-cluster/src/cluster_admin.rs`): membership counted by the same rule as `s4_cluster_nodes`, the anti-entropy, GC and scrubber counters each metric mirrors — anti-entropy rounds by outcome, ambiguous keys and whether the node runs rounds at all included.

## Credentials and Admin Tokens

The same code in CE and EE; `s4-server/src/secrets.rs` holds the rules.

- **Sources**: `S4_ROOT_USERNAME`, `S4_ROOT_PASSWORD`, `S4_ACCESS_KEY_ID`, `S4_SECRET_ACCESS_KEY`
  and `S4_JWT_SECRET` are read directly or from the file their `_FILE` form names (Docker and
  Kubernetes secrets). Both forms set, or a file that is unreadable, empty, not UTF-8 or larger
  than 64 KiB, stops the start.
- **Admin tokens** (`s4-features/src/iam/auth.rs`, `middleware/admin_auth.rs`): a token refers to
  an account. It carries `sub`, `cv` (the account's `credential_version` at issue), `iat`, `exp`,
  `jti`, and `username` and `role` for clients to show. Every admin request reads the account: the
  token is accepted only while it exists, is active and has the same `credential_version`, and the
  handlers decide by the account's current role (`AdminPrincipal`). The version grows with a new
  password, a new role, a deactivation, `POST /users/{id}/sessions/revoke` and `POST /logout`;
  tokens without `cv` (earlier releases) are refused.
- **Root** (`s4-features/src/iam/root.rs`): configured, not stored. A login under
  `S4_ROOT_USERNAME` is checked against `S4_ROOT_PASSWORD` (hashed at start); the id is a UUIDv8
  of the name, the same on every node. `__s4_iam_v2_root_state` keeps root's credential version and
  an HMAC fingerprint (keyed by the JWT secret) of the configuration; a start with another
  fingerprint raises the version. In cluster mode the state is the pool's (`ClusterControl`), and a
  revocation through one node ends root's sessions on every node. A node judges a start by the
  configuration it last started with, kept in its own storage (`__s4_iam_node_root_fingerprint`,
  never replicated; `RootStart`): an unchanged one, or the node's first start with root, asks no
  other node; a changed one reads the pool's state under the lease of IAM changes and raises it
  unless another node already raised it for this configuration (`RootState::after_change`,
  `IamStorage::change_root_state`), so a new password
  rolled through the nodes ends root's sessions once. A cluster node does that in the background,
  retried until the pool answers. The Admin API
  refuses to change root (`409 RootFromEnvironment`); a stored root user of an earlier release is
  ignored for login and listing.
- **Users** (`s4-features/src/iam/{storage,user_directory,store}.rs`): one record per user,
  `__system__/__s4_iam_v2_user_<id>` — name, password hash, role, active flag, S3 credentials and
  credential version together — so creating a user, issuing its keys and deleting it each write or
  delete one record. Lookups by id, name and access key — logins, tokens, SigV4 and SigV2 — read the
  node's own copy through `IamDirectory`: indexes in memory, built from the records at the first
  lookup and brought up to a record after every change of it; of two records of one name or key the
  one created under the later lease epoch answers (`User::created_epoch`), then the one created
  first. Every change is one `IamChange` of `IamRecordStore::begin`, made under the lease of IAM
  changes: on a single node a lock of its own, on a cluster node the lease of the pool (below),
  under which it reads its preconditions — the name free among the users a majority holds, the
  user there — writes, and releases. A cluster node's change goes through
  `s4-api/src/cluster_iam.rs` (`ClusterControl`: on every node, through a majority, a hint for a
  node that missed it, a tombstone for a delete); without a majority it answers `503`. A cluster
  node's directory learns of every record written to its storage — by a peer, a hint,
  anti-entropy or itself — from the storage adapter (`SharedStorageAdapter::observe` in
  `s4-server/src/cluster_bootstrap.rs`).
- **Lease of IAM changes** (`s4-cluster/src/iam_lease/`, protocol 8): the node a change came to
  asks every node of the pool for the next epoch (`IamLeaseAcquire`) and holds the lease once a
  majority granted it. A node grants one holder at a time for `S4_IAM_LEASE_SECS` (5) by its own
  monotonic clock, each epoch once, and keeps the highest epoch and the HLC floor in its own
  storage before it answers (`__s4_iam_node_lease`, `LeaseLedger`). A change that finds the lease
  held waits up to `S4_IAM_LEASE_WAIT_SECS` (10), then `503` with `Retry-After`; one that finds
  no majority answering, `503` at once. Every write of an epoch carries its fence (`IamLeaseFence`
  in `WriteBlob`/`DeleteBlob`): the epoch and an HLC window, above the floor — the highest HLC an
  earlier epoch may have written with, which the granting majority reports, raised to the
  release's HLC once a holder releases — and below the epoch's ceiling. Each replica, the
  holder's own included (`QuorumWriteCoordinator::with_iam_lease`), admits a client's write of the
  class only under the current epoch, inside its window, while its own grant of the epoch is live
  and not past the release (`ReplicaWriteHandler::admit`, `lease_fenced` in the answer,
  `s4_iam_fenced_writes_total`); repair copies are not fenced. A change reads its preconditions
  with `IamLeaseRead`, from a majority: each node takes the reader's epoch before it answers and
  refuses earlier epochs' writes from then on; a version the read finds on fewer than a majority —
  a change that failed — is written again under the reader's lease before the change acts on it
  (`LeaseRead::unsettled`), so no two reads disagree on what a change relied on. A holder never
  asks for an epoch it asked for before. So a change sees every change confirmed before it,
  none of an earlier lease is confirmed after its read, and every write of a later epoch outranks
  every write of an earlier one by HLC — a holder that woke up after its lease passed on cannot
  have a write win anywhere, whatever the clocks; the clocks decide only how soon a lease frees
  up. A holder renews a lease that is half spent before it writes. The model test
  (`iam_lease/model_tests.rs`) checks random histories with cut-off nodes, paused holders,
  delayed copies, restarts and anti-entropy: nothing confirmed is lost, each user's confirmed
  changes form one chain, and a name resolves to its one confirmed user. Scenario 62 stalls a
  holder between the check of its lease and its write with a test hook
  (`s4-api/src/iam_test_hooks.rs`: `S4_IAM_TEST_HOOKS_ENABLED`, `S4_IAM_TEST_STALL_USERNAME`,
  `S4_IAM_TEST_STALL_MS`; inert without the first): with its clock right the holder's own HLC is
  past the epoch's window and it sends nothing, with its clock behind the window lets the write out
  and every node that saw the next epoch fences it.
- **Checking against the node's own copy** (`s4-cluster/src/iam_catch_up/`, plan
  CLUSTER-IAM-REPLICATION.md, decision 4): logins, tokens, SigV4 and SigV2 ask no other node, so a
  cluster node checks IAM credentials only while a majority of its pool agrees with its copy.
  `IamCopy` keeps, in memory, the copy as the pool compares it — a fingerprint of the live records
  of the class (key, HLC, ETag) and the epoch, the HLC of its newest record, deletes included —
  brought up to every change by the storage adapter, as the directory is; each node announces both
  in gossip (`IamTail`, the third part of `MetaTail`). Every 250 ms `IamCatchUp` compares: a peer
  alive by SWIM that announces the same fingerprint agrees; one that announces another is asked for
  its versions (`IamVersions`, paged, with the fingerprint taken before the page) and every key it
  holds newer is settled by `Reconciler::settle` for the pair, at once; the peer then agrees while
  it announces the fingerprint caught up with. A peer that moved on since still vouches for the copy
  as of the moment that catch-up began to read its versions: the copy holds every version the peer
  held then. The copy is confirmed in `IamFreshness` as of the oldest of the newest moments a
  majority vouches for — `now` for the node and each agreeing peer, the catch-up's start for the
  others — so a pool that changes IAM without pause, whose copies seldom agree at the moment they
  are compared, still confirms them about once a catch-up (one per peer per second). A confirmed
  change is on a majority, any two majorities meet, so a copy confirmed as of `t` holds every
  change confirmed before `t`. While the copies agree no RPC is
  made — gossip carries the comparison. Until the first confirmation since the start (`starting`),
  and once none for longer than `S4_IAM_MAX_STALENESS_SECS` (30, `0` for no bound; `stale`), the
  credential gate (`CredentialGate`, `IamStorage::admit_credentials`) refuses IAM credentials with
  `503 ServiceUnavailable` and `Retry-After`, counted in `s4_iam_auth_refused_total`; root, the S3
  credentials of the environment and the IAM an earlier release left on the node pass. A request
  with an IAM key the node does not check now is tried against the environment's credentials and
  answered `503` only when its key is not theirs. `s4_iam_epoch_applied`,
  `s4_iam_replica_lag_seconds` (since the last confirmation). A node back from a restart learns its
  peers' tails from their answer to its return: gossip treats a new run of a known node as it
  treats a node never seen, and every member rebroadcasts its own metadata at once
  (`handle_notification`), rather than at its next periodic broadcast (30 s).
  `GET /api/admin/iam/status` (`s4-cluster/src/iam_status.rs`, `IamStatusSource`) answers from
  what the node holds — the gate and the last confirmation, every node's announced epoch and whether
  it agrees (`IamCatchUp::pool_view`, by the rule above), the grant of the lease the node holds out
  (`IamLeaseKeeper::live_grant`) and the adoption gate — without asking any peer.
- **Users of earlier releases** (`__s4_iam_user_*`, `__s4_iam_username_*`,
  `__s4_iam_access_key_*`): a single node turns them into records of version 2 at start and
  removes them (`IamStorage::convert_legacy`, every step repeatable), and marks in its storage
  that it holds users (`__s4_iam_node_single_users`, local). A cluster node cannot merge them — its
  copy may hold users deleted through another node — so they are its own IAM: before it joins its
  pool it turns a single node's marked users back into that form
  (`IamStorage::take_back_single_node_users`, local deletes, no tombstone), and while it holds such
  users it serves them as before, from its own storage only. A stored root without S3 credentials
  counts as no such user. **Adoption** (plan CLUSTER-IAM-REPLICATION.md, decision 8;
  `s4-features/src/iam/adoption.rs`, `s4-cluster/src/iam_adoption.rs`,
  `s4-server/src/iam_adoption.rs`): every node announces in gossip whether it keeps IAM of its own
  (`iam_adopted`, the second field of the IAM part of the metadata tail); IAM changes on a node open
  (`IamAdoptionGate`, `IamStorage::with_adoption_gate`) once every node of its pool's list is alive at
  protocol 8 and announces none, and stay open across restarts (`iam_adopted` in `cluster_meta`,
  dropped by an open without digests); until then every node answers changes `409
  IamAdoptionPending`, `/cluster/health` is at least `degraded` with `iam_adoption`, and
  `s4_iam_adoption_pending` is `1`. A pool where no node keeps any opens by itself. Otherwise
  `GET /api/admin/iam/adoption` asks every node of the pool for its own records (RPC
  `IamOwnUsers`) and builds the report: every name with its nodes, records, majority and conflicts,
  each node's answer fingerprinted, the `report_id` the fingerprint of all of them.
  `POST /api/admin/iam/adoption` (`union`, `majority`, or a list of ids, naming the `report_id`)
  needs every node's answer and the same report, then under the lease of IAM changes writes a record
  of version 2 per user taken over — the copy changed last; of one name the pool's own user, then
  the first created keeps it, the others are renamed `<name>~<8 characters of the id>` and
  disabled; ids the pool holds already are left as they are — and last the decision,
  `__s4_iam_v2_adoption`, with the report and each node's fingerprint. A node drops what it keeps
  of its own (`IamStorage::drop_legacy`) only when the decision it holds names its current
  fingerprint, and then serves the pool's users; a decision taken again after one stopped half way
  writes nothing twice.
- **Secrets of S3 credentials** (`s4-features/src/iam/secrets.rs`, plan CLUSTER-IAM-REPLICATION.md,
  decision 7): SigV4 needs the secret itself, so a record keeps it sealed with AES-256-GCM
  (`secret_key_sealed`: key id, nonce, ciphertext), the user's id and access key as associated
  data, never in clear text; a node's directory opens it into memory when it reads the record. The
  key (`SecretKeyring`): `S4_IAM_ENCRYPTION_KEY`, else HKDF-SHA256 of a configured `S4_JWT_SECRET`
  (`s4-iam-secret-v1`), else a key the node generates and keeps in its own storage
  (`__s4_iam_node_secret_key`, never replicated); `S4_IAM_ENCRYPTION_KEY_PREVIOUS`, the key derived
  from the JWT secret and the node's own key stay readable. Every write of a user record seals
  (`IamDirectory::sealed`), the conversion of a single node's earlier release included, and a
  node's own records leave it sealed (`IamOwnUsers` with `OwnRecordSealer`; the adoption
  fingerprint ignores the secret). A secret under a key the node lacks is answered `503`
  (`NotServing::SecretKeyUnknown`), for another node to check. `IamUpkeepWorker`
  (`s4-server/src/iam_upkeep.rs`, every 5 s) reports `s4_iam_records_by_key_id` and, once IAM
  changes are open and — on a cluster node — every node of the pool is alive and announces the same
  key, seals again under the lease every secret under another key or in clear text
  (`IamStorage::reseal_secrets`); it reads its own copy first and asks the pool only when there is
  something to do.
- **Configuration of the pool** (`s4-cluster/src/iam_config.rs`, decision 6): every node announces
  in gossip (`iam_config`, the third field of the IAM part of the metadata tail) 16-byte
  fingerprints of root (`HMAC(JWT secret, "root:" + name + ":" + password)`), of a configured JWT
  secret (`HMAC(secret, "jwt-secret-check")`) and of a shared encryption key; `IamConfigCheck`
  compares the live nodes of the pool every second, names a node whose value is not the majority's
  (every node when no value has one) in the log, in `s4_iam_config_mismatch{kind}` and in
  `/cluster/health` (`iam_config`), which is then `critical`. A generated JWT secret and a node's own
  key are announced as none.
- **Audit log** (`s4-features/src/iam/audit.rs`, decision 10): every change of IAM writes, in the
  same change, `__system__/__s4_iam_v2_audit_<epoch>_<micros>_<n>` — actor, action, target, the
  node it went through, the lease epoch and what changed, never a password or secret — so the key
  orders the log as the changes were made. `GET /api/admin/iam/audit` reads the node's own copy a
  page at a time; the upkeep deletes entries older than `S4_IAM_AUDIT_RETENTION_DAYS` (90) under the
  lease, once an hour. `GET /api/admin/users` pages too (`max-keys`, `continuation-token`), root
  first.
- **Admin JWT secret**: whoever holds it can sign a token for any account, root included, so the
  secret is a SuperUser credential. There is no built-in value. At startup, before the node joins
  a cluster:
  - a configured secret shorter than 32 bytes is refused: it can be guessed offline from any
    issued token;
  - unset on a single node, a random secret is generated per start, and sessions end on restart;
  - unset in cluster or gateway mode with IAM in use (`S4_ROOT_PASSWORD` set, or IAM users on
    disk), the start is refused: each node would sign with its own secret, and a token would work
    only on the node that issued it.
- **Legacy S3 keys**: `S4_ACCESS_KEY_ID` / `S4_SECRET_ACCESS_KEY` authenticate as a synthetic
  SuperUser (`env-admin`) when no IAM user holds the access key. Unset, they are random per start;
  set to an empty value, this login is off.

## Editions (CE / EE)

S4 follows an Open-Core model with two editions built from the same codebase:

- **Community Edition (CE)**: Apache 2.0. Full single-node and 3-node cluster (1 pool, RF=3, W=2, R=2). All clustering primitives (gossip, gRPC, quorum, anti-entropy, tombstone GC, CRC scrubber) are included.
- **Enterprise Edition (EE)**: Elastic License 2.0. Removes scaling limits (unlimited pools and nodes) and adds operational features (deep SHA-256 scrubber, rolling upgrades, automated node replacement, LDAP/SAML/OIDC, WebDAV, audit log).

### CE/EE Boundary

The boundary is enforced at two levels:

1. **Quantitative limits** (`ClusterLimits`): CE = 1 pool, 3 nodes. EE limits come from the Ed25519-signed license.
2. **Trait-based DI** (`ClusterServices`): EE behavioral features (deep scrubber, node replacer, etc.) are injected via trait objects. CE uses noop implementations.

`#[cfg(feature = "enterprise")]` appears **only** in `s4-server/src/edition.rs`. No feature gates in domain code.

### Docker Images

| Tag | Edition |
|-----|---------|
| `s4core:latest` | CE (default) |
| `s4core:ce` | CE (explicit alias) |
| `s4core:ee` | EE (requires `S4_LICENSE_KEY`) |

Build locally: `docker build .` (CE) or `docker build --build-arg EDITION=ee .` (EE).
